# PM 必备的最小技术心智模型

> 来自本 skill 辩论中的「前端」「后端」「前后端契约」三个视角。
> 目的:给没受过工程训练的 PM 一套**够用的比喻**,让你能指着一个 Demo 说清楚——**哪一层是真的,哪一层是布景。**

---

## 统一比喻:一家餐厅

整个软件系统就是一家餐厅。三个工程视角吵到最后,比喻自己拼成了一张完整的图:

| 系统的一层 | 餐厅角色 | 它负责什么 |
|---|---|---|
| **前端** | 大堂 + 样板间 + 摆盘 | 让客人**看到**、**点单**。摸得到,但不产生食材。 |
| **后端** | 厨房 + 冷库 + 收银台 | **什么是真的**(账)、**什么被记住**(冷库)、**谁能进厨房**(权限)。 |
| **契约(接口 / API)** | 服务员手里那张**点菜单** | 大堂和厨房互不进门,全靠这张单子对接。 |

**PM 工程判断力 = 随时知道你的 Demo 里,厨房到底存不存在。**

---

## 一、前端 = 大堂与样板间(展示层)

**前端只干两件事:把数据摆出来给人看,把用户意图收上来往后传。** 它不产生、不保存、不验证数据。

它像**样板间**:柜子摸得到,但抽屉钉死、水管没通——看着能住,一样家电都用不了。

**为什么"前端能跑通"几乎总是幻觉:**
- 前端天生能**脱离后端独立运行**,拿一批写死的假数据(mock)就能撑得像模像样。这不是 bug,是它正经的特性。
- 更坑的是:AI 为了让页面"看着正常",会**顺手造一个假的成功提示**。你以为验证了产品,其实只验证了 **AI 的想象力**。

> **核心错觉:把界面当产品。** 界面是整个系统里**最容易做的那层皮**,真相全在皮下面。AI 时代"能显示出来"几乎没难度,拿它当验收标准 = 只检查一件几乎不可能失败的事。

**前端最容易骗到你的三个地方:**
1. **把 state 当数据库:** 提示"保存成功"、列表也刷出来了,一按 F5 全没——数据只在浏览器内存的一个数组里,**从没碰过数据库**。
2. **把"没报错"当"后端真执行了":** 接支付,点击就弹"支付成功";其实后端没接通、没防重复提交,客户翻账单才发现没扣钱、或扣两笔。
3. **把"看不见"当"进不去":** 普通账号看不到"删除用户"按钮就当权限做完了——对方用 F12 或 Postman **直接调接口**就能删库。**权限只写在前端"不渲染"里,等于没有。**

---

## 二、后端 = 厨房、冷库、收银台(真相层)

菜单再精美,冷库空着就上不了菜。**后端才是"产品到底是什么"的所在地**,它只回答三个问题:**什么是真的?**(账)**什么被记住了?**(持久化)**谁能进厨房?**(鉴权)

产品对用户的**全部承诺**——"昨天存的今天还在""这数据只有你能看""这笔钱真扣了"——都兑现在后端。UI 只是这份承诺的海报。

**数据模型 = 真正的产品。** 漂亮 UI 盖在错误数据模型上,等于豪华装修压在错误地基上,只能推倒。

> **翻车现场:** 订单表里直接写死 `product_name="iPhone", price=5999`,没有独立商品表、没有外键(把两张表对上号的连接)。Demo 看不出问题。可一旦——商品改价,历史订单跟不跟?一单买多件,一行塞不下;想统计"这商品卖了多少",没有 `product_id` 根本 group 不起来——**这时不是改代码,是重建数据模型 + 迁移旧数据 + 重写每条查询。**

所以:**调 UI 之前,先把"名词和关系"画对。** 系统里有哪些东西、它们什么关系(一对多?多对多?)——画错就全盘重来。

---

## 三、契约 = 那张点菜单(接口 / API)

前端(大堂)和后端(厨房)**互不进门**,靠一张"点菜单"对接:**能点什么**(有哪些接口)、**单子怎么写**(请求带什么参数)、**上什么盘**(返回什么字段、什么类型、出错怎么说)。

> **Demo 最隐蔽的作弊就在这条线上。** 服务员不把单子递进厨房,而是从柜台下摸出一盘**预先摆好的假菜**——前端把数据写死(`const data = [...]`)。大堂一模一样、"能跑",可**根本没有厨房**。AI 最爱干这个。看懂这条线,你才知道自己在哪造假、变真要花多少钱(钱几乎全花在"补一个真厨房"上)。

**集成的缝隙:两块各自都绿,拼起来就崩。** 因为它们各自默默做了对方不认的假设,缝隙没人负责:
- 前端按 `"2026-08-18"` 显示,后端返回 Unix 时间戳 `1755500000`——各自都"对",合起来满屏 `Invalid Date`。
- 前端把 `userId` 当数字发、后端当字符串收,查不到还**不报错**,只显示"无结果"——**错得悄无声息**,最难查。

> 各自演示只是拿自己的假设考自己。**唯一算数的验证,是真实数据跑一遍完整往返**(前端 → 契约 → 后端 → 存 → 取 → 契约 → 前端)。

---

## 四、状态 vs 持久化:脑子 vs 抽屉

- **前端 state** = **脑子里正想的事**,一睡醒(刷新页面)就可能忘光。
- **数据库(持久化)** = **锁进抽屉的事**,不管睡不睡、换不换设备都在。

所以 PM 该问的不是"页面显示出来没有",而是三连问:**这个数据,活在哪里?活多久?谁能看见?**

---

## 五、鉴权:谁能进厨房

**"看不见"不等于"进不去"。** 权限只做在前端(不渲染按钮)是掩耳盗铃——真正的权限必须由后端在**每次请求时**校验"你是谁、你有资格做这件事吗"。两条底线(有真实用户时不可退让):
- **多用户隔离:** A 绝不能看到 / 改到 B 的数据。用一个全局变量存"当前用户",两人同时用就串号。
- **密钥不进前端:** API key、密码写死前端,按 F12 就能扒走。密钥一律进后端环境变量。

---

## 六、部署:"在我电脑上能跑" ≠ 交付了

系统被悄悄绑在"你这台笔记本"上(写死的本地路径、没记录的环境变量),它就不是产品,是**你桌上的手工艺品**。

> 验收标准不是"我这能跑",而是:**一台新机器,只靠文档,从零跑通。**

---

## 七、一张"你在哪里作弊"的对照表

做完一个 Demo,逐层自问一遍,就知道自己手里是"证据"还是"幻觉":

| 层 | 真的长什么样 | 作弊常见形态 | 一句话验真 |
|---|---|---|---|
| 前端展示 | 真渲染后端返回的数据 | 数据写死在前端 | 把后端关掉,页面还有数据吗? |
| 契约 / 连接 | 真发了网络请求 | 假装调用,其实读本地常量 | 打开网络面板,有真请求飞出去吗? |
| 后端逻辑 | 真算 / 真调了模型 | 返回一条提前写好的结果 | 换个没预设的输入,结果还对吗? |
| 持久化 | 关掉重开数据还在 | 只存在内存里 | 刷新 / 重启后,数据还在吗? |
| 鉴权隔离 | 每次请求都校验身份 | 权限只做在前端不渲染 | 换个身份 / 直接打接口,拦得住吗? |

---

## 八、PM 最小技术词汇表

- **前端 / 后端** —— 用户看得见的展示层 / 藏在后面的真相层。
- **API / 接口 / 契约** —— 前后端约定的"点菜单":怎么问、返回什么。
- **state / 状态** —— 前端内存里临时记的东西,刷新可能就没。
- **持久化 / 数据库** —— 真正存下、重启还在的东西。
- **数据模型 / schema** —— 系统里有哪些"名词"、什么关系,真正的产品骨架。
- **鉴权 / auth** —— 校验"你是谁、能做什么"。
- **mock / 硬编码** —— 各种假数据:从写死一个值到伪造整个接口。
- **部署 / deploy** —— 把东西搬到"别人也能访问"的地方,不只是你本机。
- **并发** —— 多人 / 多请求同时发生,很多"单人能跑"的捷径一并发就崩。
