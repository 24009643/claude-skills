# 作弊的阶梯:每一种"假"值多少钱、天花板在哪

> 来自本 skill 辩论中的「后端」「前后端契约」「速度务实派」三个视角的交汇。
> 一句话中心思想:**作弊是为了聚焦,不是为了自欺。** 会作弊的 PM,是能随时说出"我现在站在第几级、再上一级要花多少钱"的 PM。

---

## 阶梯:同一个功能,从"全假"到"全真"的六级

任何一个功能,都可以停在下面某一级。**成本不是软件的铁律,而是你选型的函数:** 手写后端时,每上一级大致翻倍,第 4→5 级尤其陡;但 2026 用 BaaS / 托管服务(Supabase、Firebase、Clerk、Auth0…,人话:别人替你搭好的现成后端),第 4、5 级几乎坍缩成同一步。不该爬时多爬是浪费,该爬时没爬是自欺——只是别再把"变真 = 天价"当默认前提。

| 级 | 作弊形态 | 成本(手写后端) | 成本(用 BaaS / 托管) | 天花板 / 它能撑住什么 |
|---|---|---|---|---|
| **1. 硬编码** | 写死的 JSON / 结果 | ~1 小时 | ~1 小时(无差别) | 只对预演过的输入有效 |
| **2. mock / stub** | 结构真、数据假 | ~半天 | ~半天(无差别) | 能演能点,存不下 |
| **3. 本地内存状态** | 增删改只活在内存 | ~1–2 天 | ~1–2 天(此级 BaaS 帮不上,但**常可直接跳到第 4 级**) | 刷新即失、单人可见 |
| **4. 真数据库** | 真落盘,重启还在 | ~数天(自己搭库、迁移、部署) | **~半天**(建表即用托管 Postgres) | 存得住,但所有人共享一份 |
| **5. 真库 + 鉴权 + 多用户** | 人人有账号,只看自己的 | **前面所有之和再翻倍**(自写会话 / 加密 / 令牌 / 隔离) | **与第 4 级同一下午**(接 Auth + 写 RLS / 安全规则) | 能真上线给陌生人用 |
| **6. 可扩展** | 并发(同时有人在用)、索引、缓存 | 视规模而定 | 托管自动扛一段,极限仍要自己调 | 扛得住量 |

> 那个历史上"最贵的悬崖"(第 4→5 级)只存在于**手写后端**那一列;托管服务已把它从悬崖压成台阶。

**PM 的误判有两代,新的更危险:**
- **旧误判(仍在):** 以为"数据能显示"(第 3 级)离"能存下、每人存自己的"(第 5 级)只差一点点。在**手写后端**里这确实差一个数量级,是后端最贵的一段路。
- **新误判(2026):** 反过来以为"接了 BaaS 就万事大吉"。BaaS 抹平的是**造轮子的成本**(会话、加密、令牌、账号界面),它**没抹平**三件事:
  1. **数据模型仍要你画对**——托管替你存,不替你设计;
  2. **多用户隔离从"没写"变成"写错"**:忘了开 RLS(行级隔离,人话:每人只能看到自己那几行),或策略写成"对所有人可见",它看起来做完了、却在**静默串数据**——对业余 PM 反而更凶;
  3. **供应商锁定是一道单向门**:某家的数据模型、鉴权、边缘函数都是私有胶水,迁出去是你**延后了、而非消除了**的成本。

## 核心案例:聪明地作弊,如何两小时打赢老实地全做

这是整个"作弊哲学"最锋利的一刀,值得单独记住。

> **要验证的问题:** 用户到底愿不愿意为"AI 帮我审合同"这件事付费?
>
> **老实全做(错误):** 搭 RAG、接文档解析、建向量库、调准确率……(注:2026 用长上下文模型把整份合同直接塞进去、免掉向量库,一个"能跑的"版本一两天就行;但把准确率调到**可信**仍要数周。)然后才能给用户看。
>
> **聪明作弊(正确):** 拿 **3 份真实合同**,自己手动丢进大模型跑一遍,把答案存成 JSON;前端做一个输入框,演出"实时生成"的样子。**两小时搞定。**
>
> 两条路回答的是**同一个问题**:用户看到这个结果,愿不愿意掏钱?一个花两小时,一个花数周,高下立判。

这个案例告诉 PM 三件事:
1. **作弊的对象,是"你不需要验证的那一切"。** 这里要验证的是"付费意愿",不是"RAG 技术可行性"——所以 RAG 全假,合同结果用真的(因为用户的付费判断依赖结果质量)。
2. **选对该作弊的层,比作弊本身更重要。** 假错了地方(比如把用户看到的结果也造假),你验证的付费意愿就是假信号。
3. **工具越省事,越要守住这条纪律。** 正因为"真做"的门槛在降低("我干脆两天真做了"的诱惑变大),越要提醒自己:你这一步要验证的是**付费意愿**,不是**技术可行性**。别用"反正做得出来"骗自己跳过了"有没有人要"。

## 纵切,不要横铺:给站住的骨架装修,别造漂亮的尸体

爬阶梯的方向也有讲究。**别把某一层(比如前端)整层做得很真很漂亮,而要切一条最细的竖线,穿透所有层。**

- **反例(横铺 / 漂亮的尸体):** 三天让 AI 做出 8 屏炫酷仪表盘,全喂假数据。真接后端时,一分页、一限流、字段对不上,8 屏全部返工。你只验证了"AI 能把界面做得漂亮"——而这件事根本不需要验证。
- **正例(纵切 / 站住的骨架):** 只做"按名字搜客户、显示他最近的订单"这一个功能,但**整条路打通**:真输入框 → 真发请求 → 真的(哪怕只有 3 行数据的)数据库 → 真查询 → 真返回 → 真渲染。它丑、只有一屏、没样式,却证明了**唯一要命的事:管子通了,数据的形状扛得住一个完整的往返。**

> 口诀:**给站住的骨架装修,别造漂亮的尸体。**
> 一条能真正走通的细线 = 证据;半个华丽的空壳 = 自欺。

配套的一条死磕原则(来自契约视角):**可以造假数据,绝不许造假连接。** mock 可以返回罐头数据,但必须走**真实的接口、真实的请求路径**。因为风险和成本几乎全在"连接与缝隙"上,数据反而最便宜;一旦假了连接,你的 Demo 对"唯一那件难事"一无所知。

## 怎么决定你该爬到第几级?——由"最大风险"决定,不由"愿景"决定

不要问"这个产品最终需要第几级",要问"**我这次要验证的那个风险,最低需要爬到第几级就能产出可信证据?**"

1. 风险在**需求**(没人要)→ 用最低级作弊(1–2 级)最快地把东西怼到用户面前。别碰后端。
2. 风险在**技术**(做不做得出)→ 只把承载那个技术风险的**一条路**爬到第 4 级真数据端到端;其余全留在 1–2 级。
3. 到了 **MVP**(验证有人真用)→ 用户核心闭环碰到的每一段,必须爬到第 5 级(持久化 + 隔离);闭环之外的邻接功能,仍然可以留在 1–2 级。

**造假与变真的分界,沿着这条"核心闭环",在 Demo → POC → MVP 三阶段逐段下移。** 越靠近"真实用户的真实行为",越不许假。

## 天花板意识:每一级捷径,都要留一句话

> 这是"天花板意识"的正典说法;别处(如 failure-catalog)只引用不重讲。

每一级作弊的天花板,其实都写在物理规律里:
- 全局变量存用户 → 天花板 = **1 个并发**;
- 前端遍历列表 → 天花板 = **几百条数据**;
- 内存状态 → 天花板 = **不刷新、单人**;
- 无索引(人话:没建"目录"的表)查询 → 天花板 = **几千行**。

**走捷径不是错,忘了天花板、还把捷径当"已验证的生产能力"报给决策者,才是错。** 所以纪律是:**在偷懒的那一行旁边,写下天花板和升级路径**(呼应 ponytail 的 `// ponytail:` 注释):

```
// 天花板:合同结果是手动跑大模型存的 3 条 JSON,只够演付费意愿;
//   一旦要真实生成,必须爬到"真接模型 + 文档解析"(第 4 级),预计一两天出能跑版、准确率调优另计
const contractResult = FAKE_RESULTS[id];
```

这句注释,就是这个 Demo 交给工程师时最值钱的"雷区地图"。没有这行字的捷径,是一颗等着别人踩中才响的地雷。

---

## 一条压舱原则(阶梯版)

> **站在"够用"的最低那一级,并且在旁边写下它的天花板。**
> 多爬一级是浪费,少写一句天花板是埋雷。
